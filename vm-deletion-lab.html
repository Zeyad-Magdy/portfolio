VM Deletion Lab: Near-Real-Time Detection in Microsoft Sentinel

Building a pipeline that catches a VM deletion within about a minute of it happening and automatically hands it to a playbook — instead of someone noticing a missing resource hours later.

Microsoft Sentinel Azure Activity Log NRT Analytics Rules Automation & Playbooks
Signal source Azure Activity Log (control-plane events) Detection latency ~1 minute (NRT rule)

01 Objective

Deleting a VM is a single, irreversible control-plane action — by the time someone notices it's gone, whatever it was doing is already down. The goal here wasn't just to detect that a deletion happened, but to detect it fast and route it straight into an automated response, without anyone having to be watching a dashboard at the time.

02 Target architecture

The pipeline needed four things wired together correctly, in order:

Azure Activity Log
→
Log Analytics workspace
→
Sentinel NRT rule
→
Automation rule
→
Logic App playbook

03 Building the pipeline

  1. Connected the Azure Activity data connector from Sentinel's Content Hub, to start ingesting subscription-level control-plane events — including resource deletions — into the workspace.
  2. Assigned an Azure Policy to deploy diagnostic settings for the Activity Log across the subscription, so activity events would flow into the Log Analytics workspace automatically going forward.
  3. Added a manual diagnostic setting forwarding the Activity Log straight to the workspace — policy-driven diagnostic settings can take a while to apply retroactively, so this kept the lab moving instead of stalling on propagation delay.
  4. Built a Near-Real-Time (NRT) analytics rule scoped to VM delete operations in the Activity Log table. NRT rules run on a roughly one-minute cadence instead of Sentinel's standard scheduled-query intervals — the difference that actually matters for something as immediate as a deletion.
  5. Granted Microsoft Sentinel the Logic App Contributor role on the resource group, so its automation rules are actually allowed to invoke playbooks. Easy step to skip, and the most common reason a rule "fires" but nothing downstream happens.
  6. Built and customized a Logic App playbook to run whenever the analytics rule triggers.
  7. Verified the Azure Activity connector was healthy and actively ingesting data before treating the pipeline as complete.

04 Closing the loop

With the connector, the rule, the permissions, and the playbook all in place, the last step was proving the pipeline actually catches something end to end:

  • Deleting a VM writes a Microsoft.Compute/virtualMachines/delete event to the Activity Log.
  • The NRT rule picks it up within roughly a minute and opens a Sentinel incident, carrying the deleted resource, the identity that ran the delete, and the source IP.
  • The automation rule attached to that analytics rule immediately hands the incident to the playbook.
  • The playbook runs its configured response — for example, notifying the security channel with the incident details and tagging it for review.

05 Takeaways

  • Most of the real engineering here wasn't the analytics rule itself — it was the plumbing in front of it. Connector, diagnostic settings, and permissions all have to be right, or the rule fires into nothing.
  • NRT rules exist specifically for scenarios like this, where "detected eventually" isn't good enough — a deletion is done the moment it happens.
  • The Logic App Contributor role assignment is the step most likely to get skipped, and the one that silently breaks everything downstream when it is.
